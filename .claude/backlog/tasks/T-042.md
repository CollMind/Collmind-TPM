## Açıklama
T-034b code-review'ında bulundu. Ajan `cancel()`'ı "kapsam dışı, güvenli boşluk" diye raporladı;
**değil** — gerçek bir açık.

`agreement.service.ts:968-1015`:
- `findById` ile **kilitsiz** okuma → `agreement.status` kontrolü **bayat bir kopya** üzerinde
- `agreementRepo.updateStatus()` → `updateUnversioned` (`agreement.repository.ts:185-193`),
  **hiçbir status precondition'ı yok**, koşulsuz `UPDATE`
- Bu PR'da eklenen `updateStatusCas` burada **kullanılmıyor**

## Somut başarısızlık senaryosu
`settlement-close.service.ts` aynı agreement'ı `pessimistic_write` ile kilitleyip `CLOSED` yazıyor.
1. T1 `cancel()` bayat "APPROVED" okur, release + cancel'a başlar
2. T2 `closeAgreement()` satırı kilitler, `CLOSED` yazıp commit eder
3. T1'in kilitsiz `updateStatus` yazımı T2'den SONRA çalışır → **`CLOSED` sessizce `CANCELLED` olur**

State machine ihlali: geçersiz bir geçiş, canlı `status` alanı yanlış. Bütçe tarafında
idempotency key sayesinde çift-release olmaz, ama **status kaybı gerçek**.

## Neden şimdi öncelikli
T-034b'den sonra `submit`/`approve`/`reject`/`close` **hepsi** transaction + FOR UPDATE +
status-CAS ile korunuyor. `cancel()` tek korumasız geçiş olarak kaldı — bariz tutarsızlık,
ve en kolay gözden kaçacak yer.

## Sonuç
`cancel()` T-034b desenine geçti: transaction → `findByIdForUpdate` (pessimistic_write,
kilit sırası `settlement-close.service.ts` ile aynı: agreement → zarf) → status guard
**kilitli satırda** → bütçe release (`queryRunner.manager`) → `updateStatusCas` →
audit **aynı transaction'da** (T-014 `{manager}` overload'u) → commit →
`flushPendingAlert` commit sonrası, kendi try/catch'inde.

**T-032'nin bilinçli asimetri kararı artık geçersiz ve kaldırıldı.** O zaman gerekçe şuydu:
*"budget release status'tan ÖNCE ve idempotency key tek seferlik → güvenli re-reserve yolu yok;
bunun yerine ERROR + `AUDIT LOG MISSING — manual reconciliation` + 500."* Gerçek transaction
gelince gerekçe ortadan kalktı — rollback ikisini birden geri alıyor.
Kanıt: `grep -c "AUDIT LOG MISSING"` → **0** (yanıltıcı yorum bırakılmadı).

## ⚖️ Kanıtın sınırı (açıkça kaydediliyor)
Ajan, HTTP seviyesinde kilitsiz-okuma penceresini **birebir yeniden üretemedi** — `close()`
doğal olarak `cancel()`'ın ön-sorgusundan önce tamamlanıyor, pencere kendiliğinden açılmıyor.
Yani [[T-034b]]'deki gibi *"korumayı sök, hata geri gelsin"* türü kanıt burada YOK
(orada kilit kaldırılınca `[200,500]` çift COMMIT çöküşü alınmıştı).

Yerine iki kanıt kondu: repository seviyesinde deterministik mutasyon-anchor testi +
gerçek eşzamanlı cancel/close e2e'si (sıra-bağımsız invaryant, 3 iterasyon).
**Ayrım kayda değer: korumanın varlığı kanıtlandı, kaldırıldığında hatanın geri geldiği
kanıtlanmadı.** Kabul edildi — status-CAS zaten yarış penceresinden bağımsız olarak
geçersiz geçişi engelliyor.
