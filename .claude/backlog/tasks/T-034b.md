## Açıklama
submit/approve/reject/returnToDraft optimistic DEĞİL. Gerekçe (tasarım §): approve()'da budget COMMIT (plan.service.ts:798) status yazımından ÖNCE çalışır → version bariyerine gelmeden para hareket eder. Sınır kuralı: insan-insan + uzun düşünme süresi → optimistic; tek transaction + para → pessimistic/status-CAS. İstisna submit(): client version'ı da doğrulanır (reserveForPlan(plan.totalSpend) görülmemiş bir spend'i rezerve edebilir).

## Sonuç
Durum geçişleri artık **gerçek transaction** içinde:
`findByIdForUpdate` (pessimistic_write) → durum guard'ı (kilitli satırda) → bütçe →
`updateStatusCas` (`WHERE status=:expected`, ikinci savunma) → `commitTransaction`.
Önceden `commitReservedForPlan` (:865) `updateStatus`'tan (:888) ÖNCE çalışıyordu — **para,
durum yazımından önce hareket ediyordu** — ve gerçek transaction yoktu (`:677`/`:1003`'te
"a real transaction would be…" yorumları duruyordu).

**Asıl kazanım: kompanzasyon → gerçek atomiklik.** T-029'dan beri süren elle geri-alma deseni
kaldırıldı; tek `rollbackTransaction` bütçe + approval-request + durum + history'yi birlikte
geri alıyor. Bu ancak [[T-014]] sayesinde mümkün oldu (audit `{manager}` overload'u) — üç tur
önce "gerçek çözüm T-014" diye düştüğümüz not karşılığını verdi.

`submit()` ek olarak client `version`'ını da doğruluyor (K5 istisnası): `reserveForPlan`
kullanıcının **görmediği** bir spend'i rezerve edebilir.
