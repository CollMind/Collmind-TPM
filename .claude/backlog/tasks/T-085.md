## Açıklama

`spend-validation.service.ts:150,163`:

```ts
const enteredValue = readEnteredRaw(pmv, mechanic);   // ← decimal kolon, transformer YOK → STRING
if (enteredValue < mechanic.minValue) { ... }         // ← min/max da STRING
if (enteredValue > mechanic.maxValue) { ... }
```

**İki taraf da string** → sözlüksel karşılaştırma. `plan_mechanic_values.entered_*` ve
`mechanics.min_value`/`max_value` kolonları `decimal` ve **bu kolonlarda** transformer
beyan edilmemiş.

⚠️ Repo genelinde transformer **vardır** (`src/database/transformers/decimal.transformer.ts`,
budget ve sales-actual entity'lerinde kullanılıyor). "String mi gelir?" **kolon başına** bir
sorudur, repo geneline genellenemez — bu task'ın ilk hâli tam bu genellemeyi yapmıştı.

## ÜÇÜNCÜ NOKTA: `activeMechanics` filtresi sıfır girilmiş mekaniği elemiyor

`spend-validation.service.ts:227-228`:

```ts
const v = readEnteredRaw(pmv, pmv.mechanic);
return v !== null && v !== undefined && v !== 0;
```

`v` transformer'sız decimal kolondan gelen **string**. `"0.0000" !== 0` → **true** (strict
eşitsizlik, farklı tipler asla eşit değil). Yani sıfır girilmiş bir mekanik **hiç elenmiyor**
ve `activeMechanics` listesinde kalıyor.

Kullanıldığı yerler: karşılıklı dışlama (mutually-exclusive) çakışma kontrolü (`:236`) ve
mekanik-başı `maxCombinedDiscountPercentage` tavanı (`:334`).

**Sonuç:** %0 girilmiş iki karşılıklı-dışlayan mekanik **çakışma hatası üretir** — oysa ikisi de
fiilen kullanılmıyor.

⚠️ **ADR 0008 ile doğrudan ilişkili:** karar "girilen `0` ile girilmemiş arasında anlam farkı
yoktur" diyor. Bu filtre tam olarak o ayrımı yapmaya çalışıyor ama **tip uyuşmazlığı yüzünden
hiç çalışmıyor.** Düzeltilince ADR 0008'e uyar hâle gelir — yani bu bir davranış değişikliği
ve kayda geçmeli.

`qa-engineer` bulgusu (T-089 spec turu), Team Lead tarafından doğrulandı.

## Yan bulgu (aynı kök neden)

`spend-validation.service.ts:134` `Number.isInteger(enteredValue)` — string'de **her zaman

Düzeltme bunu da kapsamalı.
