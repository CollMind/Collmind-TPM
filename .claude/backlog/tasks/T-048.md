## Açıklama
[[T-019]] tasarımı sırasında bulundu, **Team Lead kodda birebir doğruladı**.

`ApprovalWorkflowService#submitForApproval` (`:230-257`) bütçeyi **iki kez** rezerve etmeye
çalışıyor — önce `ON_INVOICE`, sonra `OFF_INVOICE`. Ama ikinci çağrı **sessizce hiçbir şey yapmıyor**.

### Mekanizma (üç parça birleşince)
1. **Sarmalayıcı `spendType`'ı alıp ATIYOR** (`approval-workflow.service.ts:1067-1090`):
```ts
private async reserveBudgetForPlan(..., spendType: 'ON_INVOICE'|'OFF_INVOICE', manager?) {
  // Use existing reserveForPlan but with metadata to track On/Off Invoice
  await this.budgetService.reserveForPlan(
    planId, amount, channel, periodMonth, currency, tenantId, userId, manager,
  );                                    // ← spendType HİÇ GEÇİLMİYOR
}
```
Yorum *"metadata ile izlemek için"* diyor; **metadata yok**. Kodun iddiası ile davranışı ayrışmış.

2. **Zarfta `spend_type` boyutu YOK** → iki çağrı aynı `(plan, envelope)` kovasına düşüyor.

3. **`budget.service.ts:423-428` erken dönüş:**
```ts
if (netOutstanding > 0 && envelopeReserves.length > 0) {
  return envelopeReserves[0];   // idempotent no-op
}
```
Aynı `manager` üzerinden okuduğu için OFF çağrısı, ON'un **henüz commit edilmemiş** RESERVE
satırını görüyor → `netOutstanding > 0` → **RESERVE(off) hiç yazılmıyor**.

### Etki
Plan **yalnız on-invoice tutarı kadar** bütçe tüketiyor; off-invoice harcaması **hiç encumber
edilmiyor** → zarf olduğundan **müsait görünüyor** → aşırı taahhüt mümkün.
`plans.off_invoice_spend` doğru yazılıyor, yani veri doğru, **bütçe yanlış**.

### Neden bugün patlamamış
- `plans` tablosu şu an boş
- UI ağırlıkla `POST /plans/:id/submit` (`PlanService.submit`) kullanıyor; o yol
  `plan.totalSpend` (on+off toplamı) rezerve ediyor → **toplamda doğru**
`submitForApproval` ikincil/legacy yol, ama canlı ve çağrılabilir.
