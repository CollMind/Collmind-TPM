## Sonuç
`POST /plans/:id/return-to-draft` — yalnız `REJECTED`'ten; aksi halde **409 NOT_REJECTED**.
Yetki: plan sahibi PLANNER + ADMIN; CM **403** (BRD "CM plan düzenleyemez");
T-028c scope zinciri korunur (kapsam dışı/sahip değil → **404 OUT_OF_SCOPE**).
History: mevcut `RETURNED_TO_DRAFT` enum değeri kullanıldı (**migration gerekmedi**);
eski satırlar silinmez, yeni satır eklenir; T-029 kompanzasyon deseni.
Alan temizliği: `rejectedAt/rejectedById/rejectionReason/submittedAt/submittedById/approvalRequestId`
null'a çekilir — canlı satır "güncel durum"u temsil etmeli (audit zaten history'de); ayrıca
F7 self-approval guard'ının taze `submittedById` ile çalışmasını garanti eder.

## 🔴 6. çift-sayım sınıfı hatası bulundu ve düzeltildi
`BudgetService.reserveForPlan` idempotency'si **tip-bazlıydı** ("bu plan için POSTED RESERVE var mı?").
Append-only ledger'da RESERVE satırının `txStatus`'u asla değişmez (RELEASE ayrı satır) →
reject sonrası **zaten release edilmiş** eski RESERVE "hâlâ outstanding" sanılıyor →
**resubmit'te yeni rezervasyon HİÇ oluşmuyordu** → plan bütçeyi encumber etmeden onaylanabiliyordu.
Düzeltme: **net-bazlı** idempotency (`RESERVE+COMMIT−RELEASE`) + jenerasyon-farkındalı key (`...|GEN2`).
Bu, T-030 review'ında `releaseForPlan` için düzelttiğimiz hatanın **ayna görüntüsü**; aynı kök neden:
event-sourced ledger'da "outstanding" ham satır tipiyle değil **net toplamla** hesaplanmalı.
Test edilmediği için kaçmıştı — A16 tam döngü testi yakaladı.

## SQL kanıtı (A16 tam döngü)
`history: [SUBMITTED, REJECTED, RETURNED_TO_DRAFT, SUBMITTED, APPROVED]`
`budget: RESERVE → RELEASE(reject) → (return-to-draft: DEĞİŞİKLİK YOK) → RESERVE(gen2) → RELEASE(CONVERT)+COMMIT`
460 unit + 153 e2e (her iki flag durumunda). DB invaryantları: negatif reserved 0,
available>allocated 0, terminal-state asılı rezerv 0.

## Kalan not
- `commitReservedForPlan` "en son POSTED RESERVE" varsayımına dayanıyor; çoklu envelope +
  çoklu jenerasyon karışık senaryosunda sertleştirme gerekebilir → [[T-019]] kapsamında değerlendir.
- Plan entity'sinde optimistic locking (`@VersionColumn`) **hiçbir mutasyon yolunda yok** —
  pre-existing genel boşluk, ayrı ele alınmalı.

## Açıklama
T-029 sırasında bulundu: BRD plan state machine'i
`Draft → Pending Approval → Approved/Rejected; **Rejected → Draft** (audit korunur)` diyor.
Kodda **Rejected→Draft geçişi için hiçbir endpoint/servis yolu yok**. Yalnızca
`ApprovalWorkflowService.requestChanges` var ve o `Pending → Draft` yapıyor (farklı geçiş).

Sonuç: reddedilen bir plan ölü kalıyor — planner düzeltip yeniden gönderemiyor.
