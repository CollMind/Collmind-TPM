## Sınıf: var olan ama hiç çalışmamış koruma

`postingDate` bulgusuyla ("on-invoice özelliği bugüne kadar tek bir ledger satırı bile
yazamamış") **aynı sınıf.** Kod var, test yeşil, koruma hiç ateşlememiş.

**Fark edilme yolu yok:** hata vermiyor · yanlış sonuç göstermiyor · sadece hiç çalışmıyor.

## Kök neden

`spend-validation.service.ts:261-299`:

```ts
let totalOnInvoiceDiscount = 0;                 // number
...
const entered = readEnteredValue(pmv, mechanic); // ← STRING (transformer'sız decimal kolon)
if (mechanic.mechanicType === 'PERCENT') {
  totalOnInvoiceDiscount += entered;             // ← TOPLAMA DEĞİL, BİRLEŞTİRME
}
```

`0 + "10.0000"` → `"010.0000"`. Akümülatör ilk PERCENT mekanikte **string'e dönüyor.**

**Ölçüldü (node, ampirik):**

```
1 mekanik (%10)   → "010.0000"
2 mekanik (+%5)   → "010.00005.0000"
combinedDiscount  → "010.00005.00000"
combined > 30     → false          ← Number("010.00005.00000") = NaN, NaN > n hep false
combined.toFixed(1) → TypeError: not a function
```

## Etkilenen dört koruma — hepsi sessizce devre dışı

| Satır | Koruma | Bugün |
|---|---|---|
| `:302` | `MAX_ON_INVOICE_DISCOUNT` | hiç ateşlemiyor |
| `:312` | `MAX_OFF_INVOICE_DISCOUNT` | hiç ateşlemiyor |
| `:322` | **`MAX_COMBINED_DISCOUNT = 60`** (sınıf sabiti, her koşumda çalışır) | hiç ateşlemiyor |
| `:338` | mekanik-başı `maxCombinedDiscountPercentage` | hiç ateşlemiyor |

Bir planner **%10 + %5 + %90** girse birleşik indirim kontrolü **sessizce geçer.**

⚠️ Yalnız **PERCENT** dalı kirletiyor. Diğer dal (`:280`, `:294`) `(pmv.calculatedSpend /
totalPlannedGsv) * 100` hesaplıyor — bölme/çarpma coerce ettiği için **sayı** üretiyor ve
temiz. Yani kusur mekanik tipine bağlı, ve seed'deki üç PERCENT mekaniği
(`CPP_ON_PCT`, `CPP_OFF_PCT`, `MEC-DISCOUNT`) tam olarak bu dala düşüyor.

## ⚠️ GİZLİ BOMBA: düzeltme dört `.toFixed` çağrısını İLK KEZ çalıştıracak

`:306`, `:316`, `:326`, `:342` — her biri yalnız kendi kontrolü ateşlediğinde koşuyor. Kontroller
hiç ateşlemediği için bu satırlar **bugüne kadar hiç çalışmadı.**

Karşılaştırma sayısallaşınca kontroller çalışmaya başlayacak ve `.toFixed` **ilk kez**
koşacak. Akümülatör hâlâ string olsaydı orada `TypeError` → **500** olurdu.

**Aynı task'ta çözülmeli.** Düzeltmenin doğru sırası: önce akümülatörü sayı yap, sonra
karşılaştırmaların çalıştığını doğrula, sonra `.toFixed`'lerin çalıştığını doğrula. Üçü ayrı
test istiyor — özellikle `.toFixed` yolları, çünkü onlar bu düzeltmeye kadar ölü koddu.

## Plan seviyesine de yayılıyor

`:571-583` bu değerleri FU'lar arasında topluyor: `reduce((sum, cv) => sum + cv.X, 0) / length`.
Ölçüldü:

| FU'daki PERCENT mekanik sayısı | Plan seviyesi sonuç |
|---|---|
| 1 | **10** (tesadüfen doğru — `Number("0010.0000")` = 10) |
| 2+ | **NaN** |

Yani tek mekanikli planlarda doğru görünüyor, çok mekanikli planlarda `NaN` dönüyor. Bu,
kusurun neden bugüne kadar fark edilmediğinin bir parçası olabilir.

## ⚠️ DÜZELTME NOKTASI: dönüşüm okuma yerinde DEĞİL, akümülatöre girerken

`src/common/numeric/`'in yardımcıları (`rateFromNumericString`) kullanılacak — hem ratchet
tabanı artmaz (E15: dedektör orada ateşlemiyor) hem F1'in yatırımı kullanılır.

**Ama yardımcı tek başına yetmez.** Asıl kusur akümülatörün **başlangıcı ve tipi**, tek tek
okumaların değil. Yanlış yerde dönüştürülürse semantik korunur ama **tip hâlâ karışır** —
örneğin her `entered` okumasında dönüştürüp akümülatörü olduğu gibi bırakmak sorunu çözmez
görünürken çözer, ama başka bir string kaynağı eklendiğinde sessizce geri döner.

Dönüşüm, **değerin akümülatöre girdiği noktada** ve tipi orada sabitlenerek yapılmalı.
