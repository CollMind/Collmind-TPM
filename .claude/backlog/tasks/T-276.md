## Bulgu — `ADIM3_FAZB_PLAN §5 ÖLÇÜM 2`'nin uyardığı sınıf

Swagger: *"pending approval requests **for current user**"*. Kod:

```
controller   findPending(@TenantId() t, @CurrentUser('id') userId)   ← kimlik ALINIYOR
service      approval.service.ts:263  findPendingForUser(userId, tenantId)  ← TAŞINIYOR
repository   approval.repository.ts:77
               where: { tenantId, status: PENDING, deletedAt: IsNull() }
                                     ⛔ userId WHERE'DE YOK — parametre KULLANILMIYOR
```

`userId` bir parametre olarak **alınıyor, taşınıyor, ve atılıyor**.

### Davranışsal (architect, fixture kurulup silindi)

```
fixture      requested_by_id = admin@wella.com olan bir PENDING kayıt
FINANCE token GET /approvals/pending    →  adet 1 · requestedById = ADMIN'in id'si  ⛔
POZ.KONTROL   GET /approvals/my-requests →  adet 0  (yüklemi OLAN kardeş,
                                             AYNI fixture, AYNI token)
```

Pozitif kontrol ayrımı kanıtlıyor: fixture ayırt edici, desen çalışıyor, **yüklem yok**.

📌 `ADIM3_FAZB_PLAN §5`: *"yüklem yoksa SINIF SAHTE — 'kendi kaydı' diye adlandırılan şey
aslında 'herkesin kaydı'dır."*

## ⛔ DUR — DOĞRU YÜKLEM BİR ÜRÜN KARARIDIR

```
(a) "bana ATANMIŞ onaylar"     →  approverId / approval_levels içindeki sıradaki onaycı
(b) "benim AÇTIĞIM onaylar"    →  requestedById   (ama bu zaten /my-requests)
(c) "görebildiğim kapsamdaki"  →  AccessScopeService — bir SELF yüklemi DEĞİL
```

⚠️ **Ölçüm bir cevap veremez** (`§2.4`): `Z18`'in `READ_OWN` tanımı `(a)` ile `(b)`'yi
ayırmıyor, ve `approval_levels` jsonb'si bugün **`0` satır** — semantiği koddan
okunamıyor.

📌 `(b)` seçilirse uç `/my-requests`'in **ikizi** olur (`İlke 4`) — o hâlde soru
*"bu uç neden var?"*a döner.

## Kardeş bulgu — aynı sınıf, okuma yönü

`B1`'in konusu, ama aynı ailede.
