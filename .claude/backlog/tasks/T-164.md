## Neden bu task var

Bu, bir **koruma** task'ı: bulunan şey bizim kusurumuz değil, **kaynağın** kusuru. Amaç,
ileride bir *"BRD'ye uyum"* turunun onu bize taşımasını **engellemek**.

## 1. 🟢 Sessiz sıfır — biz kaynaktan DAHA KATIYIZ, ve öyle kalmalı

BRD `§5.3 Step 2`:

```typescript
const value = context.get(depCode) || 0;   // ← eksik bağımlılık SIFIR sayılıyor
```

Bizim `formula-parser.service.ts`:

```typescript
if (context[dep] === undefined || context[dep] === null) return null;
…
if (isNaN(value)) return null;
```

### Fark bugünkü veriyle somut

`skus.cogs` **4/170 dolu**. BRD'nin satırı uygulansaydı:

```
COGS eksik → 0  →  PLANNED_COGS = 0  →  PLANNED_GP = PLANNED_TO  →  ROI şişer, RAG YEŞİL
```

**166 SKU'da ROI, maliyet sıfır sanılarak hesaplanırdı.**

⚠️ Ve BRD **kendi içinde tutarsız**: 40 satır aşağıda *Edge Case Handling*
`IF(BASE_VOL = 0, **NULL**, …)` diyor. Kaynak null propagasyonunu **istiyor**, pseudo-kodunda
**ihlal ediyor**.

⚠️ Ve [[T-135]]'in bulduğu kusur (`gpRoi: plan.overallRoi || 0`, iki canlı rota) tam olarak
**bu satırın bir kopyası** — yani kaynak kusuru zaten bir kez bize sızmış.

- [ ] `formula-parser`'ın `null` davranışını **testle pinle** (bugün pinli mi — ölç)
- [ ] Test yorumuna gerekçe: *"BRD §5.3 Step 2 `|| 0` yazıyor; bilinçli olarak
      UYULMUYOR — §2.5 ve BRD'nin kendi Edge Case Handling'i null istiyor"*
- [ ] Bir *"BRD'ye uyum"* turu bu satıra dokunursa **kırmızıya dönmeli**

## 2. ⚠️ `topologicalSort` bir yanlış adlandırma — ve biz aynısını yapıyoruz

BRD `buildDependencyGraph` kuruyor, sonra `topologicalSort` **yalnız
`calculation_order`'a göre sıralıyor** ve grafiği **hiç kullanmıyor**.

Bizde: `kpi-engine.service.ts` → `order: { calculationOrder: 'ASC' }`. **Aynı yaklaşım.**

> Ortak risk: `calculation_order` gerçek bağımlılık sırasıyla çelişirse **hiçbir şey
> yakalamaz**. Glossary *"dependency order (topological sort)"* diyor; gerçekte **elle
> atanmış bir tamsayı**.

- [ ] `dependsOnKpis` ile `calculationOrder` **tutarlı mı** — bir doğrulama yaz
      (her KPI'nin sırası, bağımlılıklarının sırasından büyük olmalı)
- [ ] Bu bir **test** olabilir (seed'e karşı), guard değil — ucuz ve tek seferlik

## 3. 📌 Kayda geçsin: `conditional` ve `javascript` tipleri bizde YOK

Ölçüm: `main.kpis` → `expression = 16 · external = 9 · user_input = 2`.

- **`javascript` yok** → H5'in tehdit modelinin dayandığı tip hiç kullanılmıyor ✅
- **`conditional` yok** → BRD'nin edge-case mekanizması kullanılmıyor; bölme-sıfır'ı
  **motor** hallediyor (`safeEval` guard'ı), formül değil. **Bizimki daha sağlam** —
  koruma formül yazarının disiplinine bağlı değil

⚠️ Sonuç: [[T-160]]'ın *"`parseConditional` BRD biçimini kabul ediyor mu"* sorusu **bugün
konusuz**; kimse `conditional` kullanmıyor.

## 📌 Kaynak bu riski **öngörmüş** ([[T-143]] turu 17 / `0035 §2`)

`§11.1 A12: COGS Data Accuracy`:

> **Assumption:** *"COGS per SKU is accurate and refreshed monthly"*
> **Risk if False:** *"**Plans approved based on incorrect profitability**, Finance loses
> confidence"*

**Ölçüm:** `skus.cogs` **4/170 dolu** — varsayım bugün **ihlal**.

> BRD'nin `|| 0` pseudo-kodu uygulansaydı, A12'nin *"Risk if False"*u **aynen**
> gerçekleşirdi: eksik COGS sıfır → maliyetsiz kâr → yanlış kârlılıkla onaylanan planlar.
>
> **Bizim `null` propagasyonumuz tam olarak bu riski kesiyor.** Bu, T-164'ün gerekçesine
> kaynak tarafından bir dayanak ekliyor.

gösterildiğini buldu. ROI yanlış değil, **yanlış görünüyor**.
